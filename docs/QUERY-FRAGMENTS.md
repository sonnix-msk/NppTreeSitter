# Подсветка фрагментов запросов SDBL внутри строк BSL — дизайн

Статус: **исследование + проверенный алгоритм; реализация в C++ не начата.**

Этот документ живёт в форке плагина (ветка `sonnix/injections`), потому что фича требует
**пропатченного** лексера и не работает на стоковом NppTreeSitter. Дистрибутив и общая часть
(грамматика, `.scm`, установщик) — в репозитории `notepadpp-bsl-highlight`.

## 1. Задача

Подсвечивать текст языка запросов 1С (SDBL) внутри строковых литералов BSL как код,
а не как одну строку. Частая ситуация — запрос склеен из кусков:

```bsl
Запрос.Текст = "ВЫБРАТЬ Т.Ссылка ИЗ " + ИмяТаблицы + " КАК Т ГДЕ " + Условие;
```

## 2. Почему это не решается грамматикой

- **Фрагмент может быть серединой запроса** (`"|ГДЕ Т.Пометка = ЛОЖЬ"`, `"И Т.Ссылка = &X"`,
  `" ИЗ "`) — как целое он грамматикой не парсится.
- Предикаты `.scm` **булевы** (`#match?`), а нам нужна **взвешенная сумма** признаков.
- В плагине **сбор инъекций не вызывает `EvaluatePredicates`** → `#match?` в
  `injections.scm` вообще игнорируется; `#strip!`/`include-children`/`injection.combined`
  не реализованы.

**Вывод:** детекция = **вероятностная оценка** (score ≥ порог), а не парсинг.
Парсер SDBL при этом остаётся **раскрашивателем**: tree-sitter терпим к ошибкам и на
середине запроса выделяет отдельные токены.

Архитектура (две независимые роли):

```
литерал/склейка → [ПОРОГ по признакам] → если «запрос»:
                    прогнать через SDBL → токены → спроецировать назад
```

## 3. Признаки и оценка

### 3.1 Лексикон ключевых слов
72 слова (RU-формы) — извлечены **из `grammars/sdbl/grammar.js`** tree-sitter-bsl v0.1.7
(источник истины, не по памяти). Вес = «сила улики» 0..1, сгруппирован по риску ложных
срабатываний. Полный список — в `tools/query-fragments/lexicon.json`.

Ориентиры:
- почти однозначные: `сгруппировать, имеющие, автоупорядочивание, уничтожить` (0.70);
- характерные: `соединение, левое/внутреннее/полное, выразить, иерархии, поместить,
  упорядочить, различные, итоги` (0.55–0.65);
- средние: `выбрать, где, из, как, между, есть, ссылка` (0.25–0.40);
- **обычные русские слова** (вес намеренно низкий): `для, значение, конец, тип, число, дата,
  строка, все, или, не, по, и, в` (0.05–0.20).

### 3.2 Регистр — МОДИФИКАТОР, не фильтр
| Регистр | Коэффициент |
|---|---|
| ВЕРХНИЙ (`ВЫБРАТЬ`) | 1.0 |
| Заглавная (`Выбрать`) | 0.6 |
| строчные/смешанный (`выбрать`) | 0.35 |

Ключевое требование: `выбрать наименование из справочник.товары` (строчными) должно
детектиться, а `выбрать всякую фигню` — нет. Регистр лишь усиливает/ослабляет вклад лексемы.

### 3.3 Структурные (регистронезависимые) признаки
- `&Имя` (параметр запроса) — 0.40 (понижено: бывает и в обычном BSL);
- `ТипМетаданных.X` (`Справочник.Товары`, `Перечисление.…`) — 0.60;
- любой `X.Y` — 0.12 (слабый);
- сильная форма `ПЕРИОДАМИ(` из `ИТОГИ … ПО …` — 0.60.

### 3.4 Формула комбинирования
```
score = strongest + bonus_factor * Σ (w_i * decay^(i-1))     # признаки по убыванию
bonus_factor = 0.5, decay = 0.5
```
**Важно:** НЕ `1 − ∏(1 − w)`. Та формула **награждала длину**: проза с несколькими
случайными словами обгоняла короткий реальный фрагмент (проверено на корпусе:
проза «В указанном периоде …» = 0.433 > реальный фрагмент «Выбрать * Из …» = 0.377).
Текущая формула этого не допускает.

### 3.5 Порог
**0.30** (подтверждён на корпусе). Серая зона ниже — красим как обычную строку
(не раздражать пользователя лучше, чем подсветить мусор).

## 4. Проверка

Харнесс `tools/query-fragments/query_scan.py` (Python) — сканирует `.bsl`, вырезает
литералы и склейки через `+`, считает score, пишет отчёт с полосами и спорными случаями.
Лексикон/параметры — из `lexicon.json` (единый источник истины для Python и C++).
Размеченные примеры и инварианты — в `tools/query-fragments/examples.md`.

Замер на реальном корпусе (7 модулей, 15 МБ, 18 921 литерал/группа; корпус **не в репо**):

| Полоса | Доля |
|---|---|

## 5. Что дальше (реализация в форке, ветка `sonnix/injections`)

**Сделано:** C++-порт скоринга (ядро фичи) — `tools/query-fragments/src/query_scorer.{h,cpp}`
(самостоятельный модуль: минимальный JSON-парсер для `lexicon.json`, UTF-8 + регистр для
ASCII/кириллицы, та же формула и признаки). Тест `scorer_test.cpp` + `build_scorer_test.cmd`.

**Сверка порта с Python:** 0 расхождений на 16 размеченных примерах и на **всех 18 921**
элементах реального корпуса (сравнение score байт-в-байт, допуск 1e-6). То есть алгоритм
перенесён точно.

Осталось:
1. **Починить сбор инъекций** — не нужно: мы не используем механизм инъекций плагина
   (он игнорирует предикаты), а делаем собственный проход (шаг 4b в `Lex()`).
2. ✅ **Проход-скоринг** — реализован (`src/QueryFragmentScorer.cpp`, шаг 4b).
3. ✅ **Склейка** — реализована: `HandleConcatGroup` разворачивает выражение `a + b + c`,
   литеральные части оцениваются вместе, переменные заменяются нейтральным плейсхолдером `X`
   (позиции сохраняются), а токены SDBL проецируются **только** на литеральные спаны.
4. **Словари/веса/порог — в JSON** (`bsl-query-fragments.json` рядом с плагином) — чтение есть.
5. Проверка — пробник `fragment_probe` (без Notepad++) и живой Notepad++.

Технические детали встраивания (важно для сопровождения):
- операнды и литералы в дереве BSL обёрнуты (`(expression (const_expression (string …)))`) —
  нужны разворачивающие помощники `UnwrapExpression` / `UnwrapToLeaf`;
- вход для SDBL строится с **сохранением длин**: кавычки и `|`-продолжения → пробелы,
  `+`-операторы и переменные → пробелы/`X`, поэтому байтовые смещения совпадают 1:1;
- захваты, попавшие на плейсхолдеры (не в литерал), не красятся.

## 6. Известный баг грамматики SDBL и защита

**Ключевые слова SDBL режут слова.** В `grammars/sdbl/grammar.js` ключи объявлены без
границы слова, а идентификатор понижен по приоритету:

```js
const keyword = (...words) => token(prec(1, caseInsensitive(words[0])));  // нет границы слова
identifier: () => token(prec(-1, /[a-zA-Zа-яА-ЯёЁ_][a-zA-Zа-яА-ЯёЁ0-9_]*/)),
```

Из-за этого короткий ключ (`по`, prec 1) перебивает более длинный идентификатор
(`ПометкаУдаления`, prec −1), и грамматика **режет слово**: `Пометка` → `BY_KEYWORD='По'` +
`identifier='метка'`. Пробник `fragment_probe` это подтверждает дословно.

**Защита у нас (не трогая грамматику):** в `AddStringFragmentHighlights`
(`TreeSitterLexer.cpp`) захват отбрасывается, если он является **частью слова** — соседний
байт является буквой/цифрой/`_`/UTF-8-продолжением (`IsWordByte`). Настоящее ключевое слово
всегда ограничено несловесными символами, поэтому корректные ключи не теряются.

Побочно: это же исправляет ложные срабатывания на любых коротких ключах внутри идентификаторов
(`по`, `из`, `как`, `в`, `и`, …).

**Отправлено в апстрим:** `alkoleft/tree-sitter-bsl` #14 (пункты 1–2 того же корня) — наш
комментарий с более полным набором примеров:
https://github.com/alkoleft/tree-sitter-bsl/issues/14#issuecomment-6222596984 (2026-10-16,
английский). До этого баг у себя лишь фильтруем (данный раздел).

## 6а. Отдельные цвета для запроса (не смешиваются с кодом)

Запрос внутри строки красится **своей палитрой**, а не цветами BSL-кода. Добавлены стили
`TSStyle::Query*` (id 14..24): `QUERY KEYWORD/IDENTIFIER/STRING/NUMBER/DATE/OPERATOR/FUNCTION/
TYPE/CONSTANT/PARAMETER/PUNCTUATION`. Их применяет `MapQueryCapture` (в `TreeSitterLexer.cpp`),
сопоставляя капчуры SDBL со стилями запроса; цвет/шрифт задаются в
`src/TreeSitterLexer.xml` (блок `treesitter.bsl`), поэтому правятся без пересборки — вручную
или через Style Configurator Notepad++ (стили видны в списке для `treesitter.bsl`).

Разбивка: ключевые слова, идентификаторы/поля, строковые и числовые/датовые литералы,
операторы, **функции (в т.ч. агрегатные: СУММА/КОЛИЧЕСТВО/ЕСТЬNULL…)**, типы (ЗНАЧЕНИЕ …),
константы (Истина/Ложь/…), параметры (`&Имя`), пунктуация.

При совпадении спанов (напр. `ЕСТЬNULL` — и функция, и `@variable`) приоритет отдан
функции/ключу (см. `prio` в проекции). Захват, являющийся частью слова, по-прежнему
отбрасывается (исправлено: проверяются **оба** граничных байта — иначе `СУММА(` ошибочно
отбрасывалась, т.к. за `(` идёт слово).

## 6б. Отдельный файл запроса (`.sdbl` / `.1cquery`) — ветка `sonnix/sdbl`

Целый файл запроса — это уже готовый SDBL, поэтому детектор (скоринг) не нужен: файл
целиком парсится грамматикой `sdbl`. Отличий от фрагментов в строке два:

1. **Палитра та же** — `MapQueryCapture`/`ResolveQueryStyle` применяются к грамматике `sdbl`
   в основном проходе (`isSdblGrammar` в `Lex()`, Step 2). Поэтому отдельный запрос выглядит
   ровно так же, как фрагмент внутри `.bsl` (зелёные агрегаты, фиолетовые функции, правило
   «скобка = функция»).
2. **Авто-детект** расширений `.sdbl` и `.1cquery` → грамматика `sdbl`
   (`kExtensionMap` в `src/dllmain.cpp`).

Конфиг: `treesitter.sdbl` (`<Language>` + `<LexerType>` в `TreeSitterLexer.xml`) со стилями
запроса 14..24. Требуется `tree-sitter-sdbl.dll` + `sdbl-highlights.scm` в `TreeSitterGrammars`
(в Extended-сборке кладутся в дистрибутив).

## 7. Открытые вопросы

- Порог 0.30 подтверждён на одном корпусе — при первом же шуме может понадобиться подстройка
  (для этого и вынесен в конфиг).
- Стоит сверить эвристики с `1c-syntax/bsl-language-server` (open-source; там SDBL-в-строках
  уже решён) — единый набор признаков был бы полезен.
- Функции/агрегаты запроса (`ЕСТЬNULL`, `ПОДСТРОКА`, `НАЧАЛОПЕРИОДА`, `ДОБАВИТЬКДАТЕ`,
  `СУММА`, …) — **не** в лексиконе (в грамматике это не `*_KEYWORD`), но часть из них —
  сильные признаки. Кандидат на второй словарь.
- **Склейка** — реализована (см. раздел 5); проверена пробником на `concat_test.bsl`
  (3 запроса-склейки детектированы, 2 прозаичные склейки — нет).
